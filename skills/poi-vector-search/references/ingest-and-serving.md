# 대량 주입과 FastAPI 서빙

## Python 데이터 파이프라인

- 공공 POI 원본의 라이선스·출처·갱신 방식과 실제 스키마를 확인한다. 원본 좌표계에서 WGS84 경도/위도로 변환하고, 유효 범위·결측·중복 ID·카테고리 표준화를 검증한다. 좌표와 원본 출처를 추적할 수 있게 한다.
- 입력을 스트리밍/청크 처리하고, 임베딩 생성과 쓰기 단계의 메모리 상한·처리량·재시도·체크포인트를 정한다. 실패 배치는 재처리 가능하도록 안정적인 키와 작업 기록을 사용한다.
- 수천만 건 초기 적재는 일반 `insert` 반복과 파일 기반 bulk import를 대표 표본으로 비교한다. 파일 포맷·크기·저장소 접근·서버 버전·인덱스 구축 시간까지 포함해 총 소요 시간을 측정한다. 데이터 증가와 갱신 경로는 별도로 설계한다.
- 임베딩 모델명·버전·차원, 정규화 방식, 생성 시각을 기록해 재임베딩과 검색 재현을 가능하게 한다. 대량 배포 전에 카운트, 유일 ID 수, 오류율, 임베딩 차원, 지역별/카테고리별 분포를 대조한다.

## FastAPI와 AI 경로

- 요청 모델에서 위도/경도 범위, 양수 반경, 허용 최대 반경, 카테고리, `limit`를 검증한다. AI 임베딩 호출과 Milvus 검색에 각각 타임아웃과 동시성 상한을 둔다.
- `AsyncMilvusClient`를 쓰는 경로는 애플리케이션 수명 주기에서 클라이언트를 관리하고, 지원되는 비동기 메서드를 `await`한다. SDK 버전별 지원 메서드와 종료 API를 확인한다. 동기 데이터 변환이나 CPU 집약 임베딩을 이벤트 루프에 직접 넣지 않는다.
- 검색 응답에는 POI ID, 카테고리, 위치와 점수의 의미를 명확히 한다. AI가 결과를 설명할 때 근거 POI를 추적할 수 있게 하고, 벡터 점수를 물리적 거리로 표시하지 않는다.
- 초기 구현은 반경+카테고리와 의미 검색을 검증 가능한 경로로 만든다. 하이브리드 검색, 리랭킹, 추가 필터는 실제 요구와 품질 측정이 생길 때 확장한다.

## 규모 검증

1. 원본과 유사한 지역·카테고리 편중을 가진 표본에서 정합성과 정확도를 검증한다.
2. 목표 건수 1천만~5천만 건의 저장량과 인덱스/메모리를 임베딩 차원, 필드 크기, 인덱스 후보별로 추정한 뒤 점진적으로 적재한다.
3. 좁은/넓은 반경, 흔한/드문 카테고리, AI 포함/미포함 질의를 섞어 p50/p95 지연 시간, 처리량, 검색 품질, 실패율을 측정한다. 숫자 목표는 제품 요구가 정해지면 기록한다.
